# IDP-35: Platform release v0.1.0: release-please, moving v0 tag, CLI installable from the tag

Epic/parent: [IDP-16](IDP-16.md)

Links: blocks [IDP-36](IDP-36.md)

## Description

## Context / why

Tenants pin the platform by tag (`service-pipeline.yml@v0`, `copier --vcs-ref`, CLI at the tag; ADR-0009). Iteration 2 must ship `v0.1.0` and a moving major tag `v0` so StudyTimer can use them.

## Acceptance criteria

* **AC-1** Given changes merged to `main`, then release-please opens or updates one release PR for the platform. That PR bumps the single platform version, updates `CHANGELOG.md` and syncs the `idp-gate` package version.
* **AC-2** Given that release PR is merged, then tag `v0.1.0` and a GitHub release are created, and the tag `v0` is moved to the same commit.
* **AC-3** (edge) Given a later `v0.x.y` release, then `v0` moves to it. Given a `v1.0.0` release, then `v0` does not move and `v1` is created. Test this with the tag-moving script's unit tests.
* **AC-4** Given tag `v0.1.0`, when I run `uv tool install "idp-gate @ git+https://github.com/suyashkunte/idp-platform@v0.1.0#subdirectory=packages/idp-gate"`, then `idp --version` prints `0.1.0`.
* **AC-5** Given the repository rulesets, then only `platform-release.yml` (the GitHub Actions app) can create or move `v*` tags. This is a human ruleset change.

## Non-functional criteria

* Actions pinned by SHA.
* The release workflow has only the permissions it needs (`contents: write`, `pull-requests: write`).

## Out of scope

* Publishing to PyPI (planned for v1).
* Publishing the chart and the plugin.
* Release notes beyond release-please's defaults.

## Interfaces / dependencies

* **Open question for the spec (blocking):** squash-merge titles today are `IDP-28: <summary>`, not Conventional Commits, so release-please cannot work out version bumps. Options:

    * (a) change the PR title convention to `feat(IDP-28): …` / `fix(IDP-28): …` (update `pr-generate` and the ruleset or PR-title check);
    * (b) release-please with `release-as` / manual bumps.

* `.github/workflows/platform-release.yml`, the release-please config and the tag ruleset are human-placed; the agent stages them under `staging/github/`.
* The tag-moving logic is an agent-editable script with unit tests.
* `idp --version` may need adding to the CLI.

## Test approach

* Unit tests for the tag-moving script, the version sync and `idp --version`.
* The first real release run is the end-to-end evidence (link the run and the tag).

## Definition of Done

* ACs traced; `make verify` green; `v0.1.0` and `v0` exist.
* `docs/platform/onboarding.md` install commands use the tag.
* CHANGELOG generated by release-please from here on.
