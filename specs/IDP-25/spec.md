# IDP-25: idp-gate: constrain the build backend for editable uv sync builds (CI and make setup)

## Context
IDP-24 (PR #9, d5c0b85) pinned hatchling with hashes, but only for the two `uv build` runs in the session fixtures of
`packages/idp-gate/tests/test_profiles.py`. idp-gate is an editable workspace member (`uv.lock`:
`source = { editable = "packages/idp-gate" }`), so every `uv sync --all-packages` builds it with hatchling and runs
`hatch_build.py`: in CI (`.github/workflows/platform-ci.yml`, step "Install workspace",
`uv sync --all-packages --frozen`) and in `make setup` (`uv sync --all-packages`). That build resolves
`build-system.requires = ["hatchling>=1.25"]` fresh from the index, not from `uv.lock`, without hashes. ADR-0012
records this as the first "Known gaps (review of IDP-24)" bullet. `uv sync` has no build-constraint flag; the
supported mechanism is `[tool.uv] build-constraint-dependencies` in the root workspace `pyproject.toml`, a protected
path that a human edits. Parent epic IDP-16; depends on IDP-24 (Done) and ADR-0012.

Facts checked in the repository (2026-10-08):
- `uv.lock` locks hatchling: one `[[package]]` entry `hatchling` `1.32.4` with dependencies `packaging` 26.3,
  `pathspec` 1.1.1, `pluggy` 1.6.0, `tomlkit` 0.15.1, `trove-classifiers` 2026.9.21.13 (none of those five has further
  dependencies). It is there because hatchling is idp-gate's only dev-group dependency
  (`[package.dev-dependencies] dev = [{ name = "hatchling" }]`), not because uv records build dependencies.
- `uv.lock` `[manifest]` today holds only `members = ["idp-gate", "idp-platform"]`; no build constraints.
- `packages/idp-gate/build-constraints.txt` pins exactly those six packages with `==` and sha256 hashes (generated by
  `uv export --frozen --package idp-gate --only-group dev --no-emit-project --output-file ...`).
- The root `pyproject.toml` `[tool.uv]` has only `package = false`; no `build-constraint-dependencies`.
- The installed editable idp-gate in the local `.venv`
  (`.venv/lib/python3.12/site-packages/idp_gate-0.1.0.dist-info/`) has `WHEEL` `Generator: hatchling 1.32.4` and
  `direct_url.json` `{"url": "file://<repo>/packages/idp-gate", "dir_info": {"editable": true}}`. So today the
  unconstrained build happens to pick the locked version, because 1.32.4 is the newest hatchling in the cache/index.
- The IDP-24 fixture builds copy only `packages/idp-gate` and `build-profiles` into a temporary tree (no root
  `pyproject.toml`) and pass `--no-config`, so the new root setting does not affect them.

## Requirements
- **AC-1** Given the root `pyproject.toml`, when the workspace is synced, then `[tool.uv] build-constraint-dependencies` pins exactly the same packages and versions as `packages/idp-gate/build-constraints.txt` (hatchling and its dependencies, all `==`).
  - "Exactly the same": the set of normalized package names (lowercase, `_`/`.` -> `-`) is equal, each version is
    equal, every root entry has the form `<name>==<version>` with no environment marker, extra or second specifier,
    and no name appears twice. Order is irrelevant. Hashes are not compared (the root list cannot carry hashes).
  - Today this means the six pins `hatchling==1.32.4`, `packaging==26.3`, `pathspec==1.1.1`, `pluggy==1.6.0`,
    `tomlkit==0.15.1`, `trove-classifiers==2026.9.21.13`. The exact snippet is in plan.md (human task H1).
  - "When the workspace is synced" is verified statically (the configuration uv reads on every sync), not by running
    `uv sync` in a test (NFR: no network, no extra builds). That uv applies the setting to the editable build is
    verified by AC-2 and by H1. ASSUMPTION A1, see Q1.
  - Red until the human edit H1 lands (the key does not exist today).
  - AMENDMENT (2026-10-10, after review loop 1, decided by the human, see Q8): for an editable build, hatchling's
    `get_requires_for_build_editable` always adds `editables~=0.3` to the build requirements. So "hatchling and its
    dependencies" for the `uv sync` build means the hatchling closure plus the `editables` closure. `editables` is
    added to idp-gate's dev group so `uv.lock` locks it, `build-constraints.txt` is regenerated to include it, the root
    list gains `editables==<locked>` (human task H2), and the drift reference becomes the union of both closures
    (task T5). The AC text above is unchanged.
- **AC-2** Given CI has run `uv sync --all-packages --frozen`, when the tests read the installed idp-gate's `dist-info/WHEEL`, then `Generator` names the hatchling version locked in `uv.lock`.
  - "The hatchling version locked in uv.lock" = the `version` of the single `[[package]]` entry named `hatchling` in
    `uv.lock` (today `1.32.4`; present because of idp-gate's dev group). The AC-3 drift test ties it to
    `build-constraints.txt` and the root list, so all three name the same version. ASSUMPTION A2, see Q2.
  - The test reads `WHEEL` through `importlib.metadata.distribution("idp-gate")` (no path guessing, no build) and
    first checks that this distribution is the editable workspace install (`direct_url.json`: `dir_info.editable` is
    true and `url` points at `<repo>/packages/idp-gate`). Otherwise it fails with a message telling the user to run
    `make setup`, rather than reading some other install.
  - The expected line is exactly `Generator: hatchling <locked version>` and it is the only `Generator:` line.
  - Runs wherever the test suite runs (locally after `make setup`, in CI after the `--frozen` sync).
- **AC-3** (edge) Given `uv.lock`, `build-constraints.txt` and the root `build-constraint-dependencies` list disagree, when the test session runs, then a drift test fails and says which source is out of date and how to regenerate it. Examples of disagreeing: only one of them was bumped, a package is missing or extra, or an entry is a range such as `hatchling>=1.25` instead of `==`.
  - The ticket writes the edge marker after the bold id; it stays outside the bold so `idp spec-trace` (regex
    `- **AC-n**`) parses it. Meaning unchanged.
  - `uv.lock` is the source of truth (it is where `uv lock --upgrade-package hatchling` moves the version). The other
    two sources are compared with the hatchling closure in `uv.lock`; a mismatch names the derived source as out of
    date:
    - `build-constraints.txt` -> "regenerate: `uv export --frozen --package idp-gate --only-group dev
      --no-emit-project --output-file packages/idp-gate/build-constraints.txt`" (unchanged IDP-24 command).
    - root list -> "a human must set `[tool.uv] build-constraint-dependencies` in the root `pyproject.toml`
      (protected path) to: <the exact expected entries>, then run `uv lock`".
  - Every failure message also lists the concrete differences (missing package, extra package, version A vs B,
    non-exact entry, duplicate entry) and ends with the bump hint: "to bump hatchling on purpose, run
    `uv lock --upgrade-package hatchling` first, then update both derived sources". This covers the case where only
    one derived source was bumped (the lock is then reported as the reference, and the hint names the bump path).
  - All problems are collected and reported in one failure (not first-error-only), so one run shows everything.
  - A missing `[tool.uv] build-constraint-dependencies` key, or a non-list value, is drift ("root list is out of
    date") with the same remedy.
  - Range or otherwise non-exact entries are drift in either derived source (`hatchling>=1.25`, `hatchling~=1.32`,
    `hatchling==1.32.*`, `hatchling===1.32.4`, `hatchling==1.32.4; python_version >= '3.12'` in the root list). In
    `build-constraints.txt`, the environment-marker suffix that `uv export` may emit stays ignored, as in IDP-24.
  - If H1 shows that uv records the build constraints in `uv.lock` (expected under `[manifest]`), the drift test also
    compares that recorded list with the root list; a mismatch says "uv.lock is out of date; run `uv lock`".
    ASSUMPTION A3, see Q3.
  - Verified with synthetic inputs for each disagreement kind (pure comparison, no files written to the repository)
    plus one check on the real repository files.
- **AC-4** Given ADR-0012, when this change merges, then its "Known gaps" no longer lists the `uv sync` gap. Instead it states the remaining limit: sync builds pin versions but not hashes.
  - The first bullet of "Known gaps (review of IDP-24)" in `docs/adr/0012-build-profiles.md` (editable installs via
    `uv sync` still build with an unconstrained, unhashed `hatchling>=1.25`) is replaced by a bullet saying: `uv sync`
    builds of idp-gate (CI, `make setup`) are version-pinned through `[tool.uv] build-constraint-dependencies`, but
    not hash-checked, because uv supports no hashes for sync build constraints. The full-environment part of the old
    bullet stays covered by the existing `PYTHONPATH`/`HATCH_BUILD_*` bullet (out of scope here).
  - A short "Implementation notes (IDP-25)" section documents the root setting, the three-way drift test, and the
    bump procedure (uv.lock, then `build-constraints.txt`, then the human root edit, then `uv lock`).
  - Verified by a small documentation test that reads the ADR's "Known gaps" section. ASSUMPTION A4, see Q4.

## Edge cases and assumptions
- Only one derived source bumped (for example the root list says `hatchling==1.33.0`, uv.lock and the file say
  `1.32.4`): the drift test reports the root list as out of date against uv.lock and prints the bump hint.
- uv.lock bumped alone (`uv lock --upgrade-package hatchling` without the follow-ups): both derived sources are
  reported, each with its own remedy.
- A package missing from or extra in a derived source (for example `trove-classifiers` dropped, or `setuptools==...`
  added) is reported by name.
- idp-gate's dev group stops containing hatchling: `uv.lock` no longer locks it, `_locked_closure` fails closed
  ("uv.lock must lock exactly one hatchling, found 0", IDP-24 helper), so AC-2 and AC-3 cannot silently pass.
- `build-constraint-dependencies` applies to every source build in the workspace, not only idp-gate. Today every
  locked third-party package installs from a wheel, so nothing else is built. A future source-built dependency whose
  build needs, for example, `packaging>=27` would fail to build; that is the signal to bump deliberately.
- A local `.venv` whose editable idp-gate was built before H1 keeps its old `WHEEL` until idp-gate is rebuilt; uv's
  cache keys for the editable install (`uv_cache.json`: package `pyproject.toml` timestamp and `src`) do not obviously
  include the root `pyproject.toml`. H1 therefore rebuilds with `--reinstall-package idp-gate`. CI always starts from
  a fresh environment.
- The AC-2 test is green locally even before H1 (the unconstrained build happened to pick 1.32.4). It turns red only
  when the index/cache offers a newer hatchling and the constraint is missing or ignored; AC-1 and AC-3 are the
  red-first tests for this change.
- ASSUMPTION A1: uv applies the root workspace `[tool.uv] build-constraint-dependencies` to the build of the editable
  member idp-gate during `uv sync --all-packages` and `uv sync --all-packages --frozen`. Not verified in this session
  (no shell access); H1 checks it by rebuilding and reading `WHEEL`.
- ASSUMPTION A2: hatchling is in `uv.lock` (verified: line `name = "hatchling"`, `version = "1.32.4"`) and AC-2's
  "version locked in uv.lock" means that entry, not a build-dependency record.
- ASSUMPTION A3: whether uv writes build constraints into `uv.lock` is unknown; the drift test's fourth comparison
  exists only if H1 shows a change to `uv.lock`.
- ASSUMPTION A4: AC-4 (a documentation change) is traced by a small text test so `idp spec-trace IDP-25` covers every
  AC.
- ASSUMPTION A5: no change to `.github/workflows/platform-ci.yml` or the root `Makefile` is needed; both keep calling
  `uv sync --all-packages [--frozen]`, which reads the new setting.

## Non-functional requirements
- No network at test time: the new tests read `uv.lock`, `packages/idp-gate/build-constraints.txt`, the root
  `pyproject.toml` and `docs/adr/0012-build-profiles.md` with `tomllib`/plain text, and the installed metadata with
  `importlib.metadata`. No subprocess.
- `uv build` still runs at most twice per test session: no new `uv build`, `uv sync` or `uv pip` call; the two IDP-24
  session fixtures are unchanged.
- No new dependencies: stdlib only (`tomllib`, `re`, `json`, `importlib.metadata`). idp-gate's
  `pyproject.toml` is unchanged; `uv.lock` changes only if `uv lock` records the build constraints (H1).
- CI `uv sync --all-packages --frozen` still passes: H1 commits `pyproject.toml` and, if changed, `uv.lock` together;
  `uv lock --check` must exit 0 afterwards.
- Protected paths: only the root `pyproject.toml` changes, by the human (H1). `.github/**`, the root `Makefile`,
  `.pre-commit-config.yaml`, `infra/**`, plugin hooks and `.claude-plugin/**` stay unchanged.
- Quality bars unchanged: mypy strict, ruff, bandit, coverage >= 85 %, diff-cover >= 80 % (test-only code change);
  `make verify` green locally and in CI; `idp spec-trace IDP-25` green.

## Out of scope
- Hash checking for `uv sync` builds (not supported by uv).
- Removing `PYTHONPATH`/`HATCH_BUILD_*` from the build environment (IDP-24 sec-1).
- Trust in the local uv cache (IDP-24 sec-2).
- Windows junctions and hardlinks.
- Changing the hatchling version, `build-system.requires`, the IDP-24 fixture flags, or the
  `build-constraints.txt` generator command.
- Making `make test` use `uv run --frozen`/`--locked` (root `Makefile`, protected; see Q5).

## Open questions
- Q1: Is a static configuration check acceptable as the AC-1 test for "when the workspace is synced", with the
  actual sync behaviour proven by AC-2 and the H1 manual check? Proposed: yes; running `uv sync` in a test would need
  the network or a second build and would break the NFRs. (A1)
- Q2: AC-2 "the hatchling version locked in uv.lock": hatchling IS in `uv.lock` today, but only as idp-gate's
  dev-group dependency, not as a recorded build dependency. Proposed interpretation: the version of that single
  `[[package]] hatchling` entry, which the AC-3 drift test ties to `build-constraints.txt` (whose `==` pin is the same
  value) and the root list. Confirm, or should AC-2 compare against the `build-constraints.txt` pin instead (same
  value today, cross-checked by the drift test either way)? (A2)
- Q3: Does `uv lock` record `build-constraint-dependencies` in `uv.lock` (for example under `[manifest]`), and does
  `uv sync --frozen` use the root `pyproject.toml` setting or the lock's copy when it builds idp-gate? `--frozen`
  does not check that the lock is fresh, so a stale lock would not fail CI's sync step; `make test` runs `uv run`
  without `--frozen`, which would silently re-lock in CI. Proposed: H1 records the facts (uv version, `uv.lock`
  diff); if `uv.lock` gains a recorded list, the drift test compares it with the root list (A3). Needs confirmation
  before T2's optional fourth comparison is implemented.
- Q4: Trace AC-4 with a documentation test reading ADR-0012's "Known gaps" (proposed, A4), or leave AC-4 to reviewer
  verification and accept that `idp spec-trace` reports it untested?
- Q5: Should `make test`/`make verify` move to `uv run --frozen` (or `--locked`) so a stale `uv.lock` cannot be
  silently rewritten during CI? Proposed: out of scope here (root `Makefile` is protected); file a follow-up if Q3
  shows the lock records build constraints.
- Q6: H1 asks the human to run `uv lock`, which may need the network to re-resolve. Proposed: try
  `uv lock --offline` first and fall back to `uv lock` (network) only if needed; the resolved versions must not
  change (only the constraint record may be added). Confirm.
- Q7: Should the root list carry a comment pointing at `build-constraints.txt` and the drift test? Proposed: yes, a
  one-line comment above the key (included in the H1 snippet). Comments are not parsed by the test.
- Q8 (DECIDED 2026-10-10 by the human: fix in this PR): the security review found that the editable build also
  installs `editables` (hatchling `build.py`, `get_requires_for_build_editable` returns
  `[*builder.config.dependencies, EDITABLES_REQUIREMENT]` with `editables~=0.3`), which was in none of the three
  sources. Pin it as described in the AC-1 amendment (tasks T5 and H2). The non-editable `uv build` runs from IDP-24
  do not request it; an extra hashed entry in `build-constraints.txt` is harmless for them.
